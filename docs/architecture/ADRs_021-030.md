## ADR-021: Frontend Architecture — Feature-Sliced Design

**Status**: Accepted
**Date**: 2026-07-20
**Deciders**: Frontend Team

### Context
Frontend needs a scalable architecture for 100+ screens across 6 workspaces (EXEC, OPP, TEN, TRUST, KNOW, ENT).

### Decision
Feature-Sliced Design (FSD) with layers:
```
app/ → providers, routing
features/ → user-facing pages (TenderListPage, SorPage)
entities/ → domain data (types + API + hooks)
widgets/ → composed UI blocks (TenderCard, BOQTable)
shared/ → reusable primitives (Button, Card, Badge)
layouts/ → page layouts (ScreenTemplate, AppShell)
providers/ → context providers (React Query, Zustand)
hooks/ → data hooks (useTenderList, useSorSearch)
```

### Consequences
- ✅ Clear dependency direction (top-down)
- ✅ Feature isolation (each feature is self-contained)
- ✅ Reusable primitives in shared/
- ⚠️ Learning curve for new developers
- ⚠️ More files per feature than flat structure

## ADR-022: API Versioning Strategy

**Status**: Accepted
**Date**: 2026-07-20
**Deciders**: Backend Team

### Context
API evolving from v1 to v2 with breaking changes (enterprise features, RBAC).

### Decision
- `/api/v1/` — stable, backward-compatible
- `/api/v2/` — new features, may break v1 contracts
- Version at router prefix level, not URL path
- Deprecated endpoints return `Sunset` header + 30-day notice

### Consequences
- ✅ Non-breaking evolution
- ✅ Client migration window
- ⚠️ Dual maintenance cost
- ⚠️ Version sprawl if not disciplined

## ADR-023: Caching Strategy

**Status**: Accepted
**Date**: 2026-07-20
**Deciders**: Backend Team

### Context
Multiple data access patterns: hot paths (SOR rates), cold paths (historical awards), computed paths (ML predictions).

### Decision
| Layer | What | TTL | Invalidation |
|-------|------|-----|-------------|
| In-Memory | SOR rates, config | Permanent | On startup only |
| Redis | Session, rate limits, distributed locks | 5min-24h | Explicit |
| Redis | Brain knowledge cache | 5min | Write-through on store |
| PostgreSQL | All persistent data | — | Source of truth |

### Consequences
- ✅ Hot paths served from memory (< 1ms)
- ✅ Redis shared across API replicas
- ⚠️ Cache coherence on multi-replica (write-through mitigates)
- ⚠️ Memory pressure for large SOR datasets (~4500 rows, acceptable)

## ADR-024: Error Handling & Resilience

**Status**: Accepted
**Date**: 2026-07-20
**Deciders**: Backend Team

### Context
49 agents + external integrations (e-GP, material sites) create many failure modes.

### Decision
1. **Agent failures**: Agent catches exception, returns `AgentResult(status=FAILED, error=...)`. Pipeline continues with partial context.
2. **External call failures**: 3x retry with exponential backoff. Circuit breaker for repeated failures.
3. **DB failures**: FastAPI returns 503 with `Retry-After` header.
4. **Validation errors**: 422 with structured Pydantic error response.

### Error Response Format
```json
{
  "error": "error_code",
  "message": "Human-readable description",
  "details": { "field": "value" },
  "request_id": "uuid"
}
```

### Consequences
- ✅ Graceful degradation (pipeline continues)
- ✅ Structured error responses
- ⚠️ Agent errors may be silently swallowed by pipeline
- ⚠️ Circuit breaker state needs monitoring

## ADR-025: File Storage Strategy

**Status**: Accepted
**Date**: 2026-07-20
**Deciders**: DevOps Team

### Context
Tender documents (PDFs, DOCX), generated reports (Excel), uploaded BOQs.

### Decision
- **Development**: Local filesystem `backend/uploads/`
- **Production**: MinIO (S3-compatible) or local filesystem
- **File organization**: `{tender_id}/{category}/{filename}`
- **Lifecycle**: Uploaded files 90-day retention; reports 1-year; tenders permanent

### Consequences
- ✅ S3-compatible for cloud migration
- ✅ Organized by tender_id for easy cleanup
- ⚠️ No file versioning (deleted = gone)
- ⚠️ Local filesystem not shared across replicas

## ADR-026: Search Architecture

**Status**: Accepted
**Date**: 2026-07-20
**Deciders**: Backend Team

### Context
Search across tenders, awards, contractors, and knowledge entries.

### Decision
PostgreSQL-native search:
- **Full-text search**: `tsvector` + `tsvector @@ plainto_tsquery`
- **Fuzzy matching**: `pg_trgm` extension for trigram similarity
- **Prefix matching**: Standard `LIKE` for code lookups
- **Composite ranking**: ts_rank + similarity score

### Search Endpoints
| Endpoint | Scope | Method |
|----------|-------|--------|
| `/api/search/tenders` | procurement_tenders | FTS + trigram |
| `/api/search/awards` | award_records_v2 | FTS + trigram |
| `/api/search/contractors` | contractors + aliases | FTS + trigram |
| `/api/search/global` | All tables | Union + rank |

### Consequences
- ✅ No external search dependency (Elasticsearch)
- ✅ Leverages PostgreSQL's mature FTS
- ⚠️ Large dataset performance needs indexing
- ⚠️ No faceted search (can add later)

## ADR-027: Real-time Notifications

**Status**: Accepted
**Date**: 2026-07-20
**Deciders**: Backend Team

### Context
Users need live updates on agent progress, tender status changes, webhook deliveries.

### Decision
- **Server-Sent Events (SSE)** for one-way server→client push
- **WebSocket** only for bidirectional agent chat
- **Webhook** for external system integration
- **In-app notifications** stored in `notification_events` table

### Consequences
- ✅ SSE simpler than WebSocket for most use cases
- ✅ Webhook for external integration
- ⚠️ SSE doesn't survive proxy timeouts (mitigated by keepalive)
- ⚠️ WebSocket adds complexity for limited use cases

## ADR-028: Data Export & Reporting

**Status**: Accepted
**Date**: 2026-07-20
**Deciders**: Backend Team

### Context
Users need Excel/PDF exports of comparisons, rate analysis, executive reports.

### Decision
- **Excel**: openpyxl generation (async via Celery for large reports)
- **PDF**: ReportLab or WeasyPrint for formatted reports
- **Async**: Any export >5s goes through Celery `job_id` pattern
- **Storage**: Generated files stored in `reports/` directory, 1-year retention

### Consequences
- ✅ Consistent export format
- ✅ Async for large reports
- ⚠️ PDF generation adds dependency
- ⚠️ Storage management needed

## ADR-029: Agent Testing Strategy

**Status**: Accepted
**Date**: 2026-07-20
**Deciders**: QA Team

### Context
49 agents with complex dependencies need testing.

### Decision
| Level | What | Tool | Frequency |
|-------|------|------|-----------|
| Unit | Individual agent logic | pytest | Every commit |
| Integration | Agent + DB | pytest + testcontainers | Every PR |
| E2E | Full pipeline | pytest + mock e-GP | Weekly |
| Golden | SOR matching accuracy | pytest + known outputs | Every PR |

### Test Fixtures
- `conftest.py`: Shared test DB, mock e-GP responses
- `test_sor_golden.py`: 100+ known SOR matches
- `test_boq_golden.py`: 10+ known BOQ comparisons

### Consequences
- ✅ Multiple safety nets
- ✅ Golden tests catch SOR regressions
- ⚠️ Test DB maintenance overhead
- ⚠️ Mock e-GP may miss real-world issues

## ADR-030: API Rate Limiting & Quotas

**Status**: Accepted
**Date**: 2026-07-20
**Deciders**: Backend Team

### Context
Multi-tenant SaaS needs per-tenant rate limiting and subscription quotas.

### Decision
| Layer | Mechanism | Scope |
|-------|-----------|-------|
| Rate Limit | Redis sliding window | Per tenant per endpoint |
| Quota | PostgreSQL `quota_usage` | Per tenant per resource |
| Agent Limits | Redis semaphore | Per agent concurrent runs |

### Rate Limits
| Tier | API Calls/min | BOQ Comparisons/month | Agent Runs/month |
|------|--------------|----------------------|-----------------|
| Free | 60 | 10 | 5 |
| Pro | 300 | 100 | 50 |
| Enterprise | Custom | Custom | Custom |

### Consequences
- ✅ Fair usage across tenants
- ✅ Quota enforcement prevents abuse
- ⚠️ Redis dependency for rate limiting
- ⚠️ Quota tracking adds DB overhead
